3. Step 1: Data Collection
This is the foundation. Bad data means bad recommendations, whatever the model.
3.1 What to track
Behavioral events (anonymous and logged-in):
product_view (with time spent on page)
product_click (from a list or carousel)
add_to_cart, remove_from_cart
wishlist_add
checkout_start, purchase
scroll_depth, size_chart_opened, image_zoom
filter_applied (size, color, price range)
Search data: query text, results shown, which result was clicked, and "zero results" queries.
Orders: order items, size, color, price, discount used, returns and return reasons, payment method, delivery pincode.
Catalog: title, description, category, brand, color, fabric, fit, gender, season, price, images, stock by size, tags.
User: user ID, signup date, city, device. Gender and age only if the user provides them.
3.2 Event schema
{
  "event_id": "uuid",
  "event_type": "add_to_cart",
  "timestamp": "2026-10-01T10:15:30Z",
  "user_id": "u_123",
  "anonymous_id": "a_abc",
  "session_id": "s_789",
  "product_id": "p_456",
  "properties": {"size": "M", "price": 1299, "source": "homepage_reco", "position": 3},
  "device": "mobile"
}

Three details matter here:
Anonymous ID: a cookie or device ID, so you can track visitors before login. When they log in, stitch anonymous_id to user_id so their history merges.
Log the source and position of every recommendation shown (impressions). You need this later to measure performance and correct for position bias.
Session ID: a session is a group of events with a gap of at most 30 minutes between them.
Tools: build your own tracker, or use Segment, RudderStack (open source), Snowplow, or GA4 export to BigQuery to save time.

score = weight x e^(-lambda x days_ago)

This produces the key table, the user-item interaction matrix. Other features to compute:
User features: average order value, preferred colors/brands/categories, price range, usual size, days since last order, discount sensitivity.
Item features: popularity (7/30 day), conversion rate, return rate, price, margin, text and image embeddings.
Context features: time of day, device, season, location.
5. Step 3: The Concepts
5.1 Implicit vs explicit feedback
Explicit feedback is a rating or a like. In ecommerce, almost all your data is implicit: clicks, carts, purchases. A user not clicking something does not mean they dislike it; they may never have seen it. Models for implicit data (like ALS and BPR below) treat this carefully.
5.2 Collaborative Filtering (CF)
"People who behave like you liked these things."
User-based CF: find users with similar histories and recommend what they bought. It does not scale well.
Item-based CF: two items are similar if the same people interact with both. Compute cosine similarity between item columns of the interaction matrix. It is stable, scalable, and powers "People also bought".
Matrix Factorization (MF): compress the huge sparse matrix (users x items) into two small dense matrices: user vectors and item vectors (e.g. 64 dimensions each). The dot product of a user vector and an item vector predicts the user's interest.
R (users x items)  ~=  U (users x k) . V^T (k x items)

ALS (Alternating Least Squares) is the standard algorithm for implicit data. Library: implicit in Python.
BPR (Bayesian Personalized Ranking): trains the model so that items a user interacted with score higher than items they did not.
Weakness: the cold-start problem. A new user or new product has no interactions.
5.3 Content-Based Filtering
"You liked this item, so here are items with similar attributes."
Convert product text to vectors (TF-IDF, or better, sentence embeddings).
Convert product images to vectors using a vision model (CLIP, ResNet). For fashion this is very powerful because it captures color, pattern, and style.
Combine into one item embedding, then find the nearest neighbors.
It solves the new-product cold start, because a new product has images and text from day one.
5.4 Embeddings
An embedding is a list of numbers (a vector) representing something so that similar things sit close together in space. Your products, users, and search queries can all live in the same vector space. Recommendation becomes "find the nearest vectors".
5.5 Approximate Nearest Neighbor (ANN) search
With 100k products, comparing against every vector for every request is too slow. ANN indexes (FAISS, HNSW, ScaNN, or a vector DB like Qdrant, Milvus, pgvector) find the top-K nearest vectors in milliseconds.
5.6 Two-Tower model (deep learning retrieval)
A neural network with two branches:
User tower: input is user features and recent history, output is a user vector.
Item tower: input is item features and embeddings, output is an item vector.
Train it so purchased/clicked pairs have a high dot product and random pairs have a low one. Item vectors are pre-computed and stored in the ANN index. At request time you compute only the user vector and search. This is the industry standard at large platforms like YouTube, Pinterest, and fashion marketplaces.
5.7 Session-based recommendation
Many visitors are anonymous or new, with no long history. Their current session is the best signal: viewed black jeans, then white sneakers, then a belt.
Simple: item-to-item co-occurrence within sessions.
Word2Vec on sessions (Item2Vec / Prod2Vec): treat each session as a sentence and each product as a word. Cheap and works surprisingly well.
Advanced: GRU4Rec, SASRec, BERT4Rec, which are sequence models (RNN or Transformer) that predict the next item.
5.8 Learning to Rank (LTR)
Retrieval gives you roughly 200-500 candidates. The ranking model orders them precisely using many more features (user-item affinity, price match, popularity, return rate, stock, recency).
Typical model: LightGBM / XGBoost with the LambdaRank objective.
Training data: impressions labeled 1 (clicked/bought) or 0 (shown, ignored).
Features: the retrieval score plus everything from section 4.
5.9 Search personalization
Search itself is a separate system (Elasticsearch / OpenSearch / Algolia / Typesense), but you add:
Query understanding, such as spelling correction and synonyms ("tee" = "t-shirt").
Re-ranking of results using the user's profile (a user who buys Nike sees Nike first).
Search history as a signal: queries are strong intent ("blue linen shirt" tells you color, fabric, and category).
A semantic search layer with embeddings, so "something to wear at a beach wedding" returns relevant results.

5.11 Re-ranking and business rules
After the ranker, apply final adjustments:
Diversity (MMR, Maximal Marginal Relevance): do not show 10 near-identical black T-shirts.
Filter out: out-of-stock or size-unavailable items, items already purchased (except consumables like socks), gender mismatch.
Boost: high-margin items, new arrivals, items on sale.
Penalize: high return-rate items.
5.12 Exploration vs exploitation
If you only show what the model is sure about, you never learn about new items. Use epsilon-greedy or Thompson sampling / bandits to show a small share (5-10%) of exploratory items.
5.13 Fashion-specific considerations
Size availability: do not recommend a product where the user's usual size is sold out.
Returns: recommend fits that are less likely to be returned.
Seasonality: Diwali, wedding season, monsoon, winter. Use time-aware popularity.
Complementary items: "complete the look" (shirt, trousers, shoes) is different from "similar items". It needs a model trained on items bought together across categories.
Price sensitivity: match the user's typical price band.
6. Step 4: The Two-Stage Pipeline in Detail
Production systems never score every product with a heavy model. They use a funnel:
All products (e.g. 50,000)
       |
STAGE 1: CANDIDATE GENERATION (fast, recall-focused)
  - ALS / two-tower nearest neighbors   -> 100
  - Session-based (recent views)        -> 100
  - Content similar to last purchase    -> 50
  - Trending in user's category/city    -> 50
  - Search-intent matches               -> 50
       |  merge + deduplicate -> ~300 candidates
       v
STAGE 2: RANKING (slow, precision-focused)
  LightGBM scores each candidate using ~50 features
       |  -> top 50
       v
STAGE 3: RE-RANKING
  diversity, stock, business rules
       |
       v
FINAL: top 10-20 shown

Why it works: stage 1 is cheap and casts a wide net, so it needs high recall. Stage 2 is expensive but runs on only a few hundred items, so it can afford rich features.
7. Step 5: Evaluation
7.1 Offline (before launch)
Split data by time: train on days 1-60, test on days 61-67. Never split randomly, because that leaks the future into training.
Metric
Meaning
Recall@K / Hit Rate@K
Did the item the user actually bought appear in the top K?
Precision@K
Share of the top K that were relevant
MAP, NDCG@K
Rewards putting the correct items higher in the list
Coverage
How much of the catalog gets recommended
Diversity / Novelty
Variety and non-obviousness

7.2 Online (the real test): A/B testing
Randomly split users into control (existing site, or popularity-based) and treatment (AI). Measure:
Click-through rate on recommendations
Add-to-cart rate
Conversion rate
Revenue per session / per visitor (the most important)
Average order value, return rate
Run for at least 2 full weeks, and wait for statistical significance.
8. Step 6: Serving (How It Works at Request Time)
Example: a user opens the homepage.
The frontend calls GET /recommendations?user_id=u_123&placement=home.
The serving API (FastAPI) fetches user features from Redis, including recent session items.
It builds the user vector (user tower or ALS vector).
It queries the vector index for candidates (~10 ms).
It merges the other candidate sources (trending, session-based).
It fetches item features and runs the LightGBM ranker (~20 ms).
It applies re-ranking and filters (stock, already purchased).
It returns product IDs, and the frontend renders the carousel.
It logs an impression event with a request ID.
The target is under 100-200 ms. To hit it:
Pre-compute item embeddings and popular lists in batch (daily).
Cache results for anonymous or cold users.
Always have a fallback (best sellers) if anything fails or times out.
Batch vs real-time: heavy training runs offline (nightly or weekly). Session features update in real time, so recommendations react immediately when a user clicks something.
9. Step 7: The Feedback Loop
Every impression, click, and purchase from the recommendation widgets is logged and becomes tomorrow's training data. Two things to watch:
Position bias: items at position 1 get clicked more just because of where they are. Log position and use it as a training feature (or correct for it).
Feedback loops / popularity bias: the model recommends popular items, so they get more clicks, so they become more popular. Counter it with exploration and diversity.
10. Step 8: Monitoring and MLOps
Data drift: has user behavior or the catalog changed?
Model metrics: daily CTR / conversion per placement.
Pipeline health: failed jobs, stale embeddings, latency spikes.
Retraining: automated schedule, with a model registry (MLflow) and the ability to roll back.
Bot filtering: remove crawlers from the training data.

14. Privacy and Legal
Since you operate in India, follow the DPDP Act 2023: get consent for tracking, and offer a way to withdraw it and delete data. If you serve EU customers, GDPR applies too.
Do not use sensitive attributes to recommend in ways that could feel invasive.
Store personal data securely, and hash or pseudonymize IDs in the analytics pipeline.
This is general guidance, not legal advice. Have a lawyer review your consent and data-retention setup.
15. Common Mistakes
Building complex models before the tracking data is clean.
Random train/test splits (data leakage).
Judging only by offline metrics and skipping A/B tests.
Recommending out-of-stock or wrong-size items.
Ignoring returns, which causes high sales but also high returns.
Having no fallback, so the widget is empty when the model fails.
Not logging impressions, which makes future improvement impossible.
16. What To Do First
Add event tracking and impression logging this week.
Ship simple "similar items" and "recently viewed" (quick wins).
Build item-based CF + image embeddings, then A/B test.
Layer on personalization, ranking, and search once data volume grows.

17.4 How accurate should recommendations be?
"Accuracy" here is not classification accuracy. A normal click-through rate on recommendation widgets is in the low single digits to roughly 10%, so set targets relative to your baseline:
Offline: beat a "best sellers" baseline on Recall@20 and NDCG@10 using time-based splits, often by 20-50% or more.
Online: a significant lift in conversion or revenue per visitor over the control group. Even 3-8% is a strong result.
Hard constraints that must be 100% accurate: no out-of-stock, wrong-size, already-purchased or wrong-gender/category items.
The target is not "90%". It is "measurably better than what we have now, with zero hard-rule violations".

17.7 How will we measure success?
Primary: revenue per visitor (or per session) in an A/B test, run for at least 2 full weeks.
Supporting: recommendation CTR, add-to-cart rate from recommendations, conversion rate, average order value, items per order.
Guardrails (must not get worse): return rate, page load time, bounce rate, complaints and unsubscribes.
Health: catalog coverage, diversity, share of revenue coming from recommendations.
Keep a holdout group (for example 5-10% of users) with no AI recommendations, so you can prove the long-term effect, since short-term clicks can mislead.
17.8 What happens when AI recommends irrelevant products?
This will happen, so design for it in layers:
Prevent with rules. Filter out-of-stock, wrong-size, wrong-gender and already-purchased items. Apply diversity so one bad guess does not fill the whole row.
Fall back. If confidence is low or the user is new, show best sellers or trending items in the relevant category.
Let users correct it. Add "not interested" and "hide this" controls and use them as strong negative signals.
Detect it. Monitor CTR drops, high return rates and zero-click widgets per placement, set alerts, and review real recommendations for sample user profiles each week.
Recover. Keep model versions in a registry for quick rollback, and use a feature flag to switch the AI off per placement without a deploy.
Learn. Ignored impressions feed back into training as negatives.
Because everything is A/B tested, a bad model affects only a small share of traffic before it is caught.

Sūtra Atelier: Planned Improvements (Product Recommendation System)
Oct 2, 2026 · @Apurv Raj
Goal
The recommendation system helps shoppers find the next handloom piece they will love, while keeping the calm, luxury feel of the store.
The first release uses product data only (similar pieces and "complete the look"), so it works before there is much purchase history. Personalisation comes later, once there is enough data to justify it. Everything runs on the existing Next.js and Supabase stack, with no new servers to start.

How it will work
The system narrows the catalog in a few steps, and a safe default is always shown if anything fails.
Collect events. Log product views, wishlist adds, bag adds, purchases, and which recommendations were shown and where. Guests get an anonymous ID that is joined to their account when they log in.
Build candidates. Gather pieces from three sources: similar products (embedding plus attribute match), pieces bought together, and new or popular items.
Apply hard rules. Remove sold-out items and sizes, items already in the bag or bought, and inactive products. Push down pieces with a high return rate.
Rank. Start with a weighted score in SQL (similarity, popularity, recency, return rate). Add a learned ranking model only when there is enough data to train one.
Diversify and cap. Show four to eight pieces with a mix of categories and prices, and no near-duplicates.
Serve safely. A read-only API route returns the list with caching. If it fails or times out, the page shows the curated fallback.
Measure. Track impressions, clicks and add-to-bag rate against a small holdout group that sees no recommendations.
Customer and admin sessions stay unchanged. Refund details such as UPI or bank accounts must never be used as a signal.
Suggested build order
This order is my suggestion, sized for a boutique catalog: move to the next phase only when the previous one shows a measurable lift.
Phase 0, foundations. Add the events table and anonymous ID, clean up product attributes, and let admins pair pieces for "complete the look".
Phase 1, rules and curation. Ship new arrivals, popular-in-category and curated pairings. This gives a baseline to beat.
Phase 2, similar pieces. Embed product images and descriptions, enable pgvector, and show similar pieces on the product page. Compare against the Phase 1 baseline.
Phase 3, behaviour. Add "often bought together" once there are enough orders, and use return rate as a ranking signal.
Phase 4, personalisation. Rank by each shopper's history and add opt-in back-in-stock messages, only if the data supports it.
Risks and open decisions
The main risk is building something clever for a catalog too small to need it, so the early phases lean on curation and product data.
Data volume. Behaviour-based recommendations need thousands of purchases to work well. Open question: how many products and orders does Sūtra have today?
Privacy. Tracking needs a clear consent notice under India's DPDP Act. Keep events pseudonymous and never use addresses, phone numbers or payment details. I am not a lawyer, so have this checked.
Build or buy. Building inside Supabase keeps cost and stack simple. A hosted recommendation service is an alternative; decide after the Phase 1 baseline.
Brand feel. A few well-chosen pieces suit a luxury store better than endless carousels. Give admins a way to pin or block items.
Limited stock. Limited-run pieces sell out, and recommending a sold-out item frustrates shoppers, so always filter on live stock.
Cold start. New pieces and new visitors have no history. Product-based similarity and curated lists cover them.
